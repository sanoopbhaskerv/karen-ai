# Karen entry guide for the 2026 subdistrict Science Working Model

Karen is being prepared for the **Science Fair Working Model** at the 2026 subdistrict Sasthrolsavam. For a pupil currently in classes 8–10, the expected section is **HS** and the catalogue item is **115 Working Model**. The school's confirmed entry is the authority for the actual section and item. This public preparation guide does not need the pupil's name, class section or school identity. [2026 official catalogue](https://mela.kite.kerala.gov.in/2026/state/index.php/publics/item_list), [manual printed page 40, PDF page 51](https://mela.kite.kerala.gov.in/2025/entry_forms/sasthrolsavam_manual_2025.pdf#page=51)

## Anonymous presentation and registration

At the user's request, Karen's exhibition replies and interface should describe the project without disclosing the pupils' names, school, class section or home details. Keep personal biographies out of the assistant's saved facts and any future exhibition-history prompt material. A neutral answer can explain Karen's components, operation and actual student contribution.

That presentation choice does not remove the need for truthful organiser-facing registration or genuine construction evidence. Keep the registered pupils' participation visible to the evaluators through the required video and explanation. The inspected general and Working Model provisions did not establish the pasted blanket ban on school uniforms or badges; a later applicable local notice could add conditions. The verified school/district-name anonymity rule described in [RULES.md](RULES.md) concerns Science Magazine and should not be extended to every item without evidence.

## Settle the participant count before final registration

Using Arduino tools, an ESP32 or other electronic hardware does not make an entry an individual event. The formal competition item determines the participant count.

For HS Science Working Model, the manual specifies **two pupils per entry**. A separate general science note requires the prescribed number of pupils in group events to participate. The catalogue's maximum of two alone would only establish an upper bound; the manual supplies the stronger two-pupil requirement. A single school entry or one winning team advancing does not mean one pupil. [Manual printed pages 40–41, PDF pages 51–52](https://mela.kite.kerala.gov.in/2025/entry_forms/sasthrolsavam_manual_2025.pdf#page=51), [printed page 44, PDF page 55, note 3](https://mela.kite.kerala.gov.in/2025/entry_forms/sasthrolsavam_manual_2025.pdf#page=55)

The current evidence therefore does **not** establish an individual exception for Karen. The school should reconcile the planned one-pupil entry against its confirmed registration and any later organising circular. If an organiser has authorised an exception, retain that written instruction with the entry records. A lead builder can still be one person, but a required teammate must participate and understand the exhibit.

## Explain what Karen currently does

The inspected repository uses an ESP32-family controller, a microphone and an amplifier/speaker for the physical interface. A Python/Flask backend handles the service calls. The exact controller build can be classic ESP32 or ESP32-S3; confirm the actual board rather than describing every Arduino-compatible board as the same device. [README](../../../README.md), [firmware](../../../firmware/karen_ai/karen_ai.ino)

```text
Spoken Malayalam question
  → microphone and ESP32 audio capture
  → WiFi upload to the Python backend
  → Google speech recognition produces question text
  → Gemini produces the Malayalam reply
  → gTTS produces reply audio
  → MP3 returned to ESP32
  → amplifier and speaker
```

In the repository's local setup the backend runs on the computer. With a separately configured hosted setup, that server location can change; the board still needs the configured server and online services. The ESP32 does not run Gemini locally. The backend sends recorded audio to recognition, and text/context to Gemini; voice synthesis is another online step. [Provider implementation](../../../app.py), [local architecture guide](../../../README.md#1-know-what-each-part-does)

The saved facts file is supplied as prompt context on each request. Conversation context is kept in memory for recent exchanges. This implementation does not establish a locally trained Malayalam language model, an offline speech assistant, or completed fine-tuning. A future exhibition-history collection will be a knowledge resource; collecting it alone does not change the model's weights. [Context assembly and provider calls](../../../app.py)

The pupil should distinguish **what the system does** from **which parts they personally made**. One possible explanation, adjusted to the actual contributions, is:

> Karen is a Malayalam voice assistant built by integrating a microphone, ESP32, server software and online AI services. The board handles recording and playback; the cloud services recognise speech, generate a reply and produce speech. My contribution was [state the work actually done], and I used [name the tools, libraries and help actually received].

A simple Malayalam opening could be:

> കാരെൻ മലയാളത്തിൽ ചോദ്യങ്ങൾ കേട്ട് ചെറിയ മറുപടികൾ പറയുന്ന ശബ്ദസഹായിയാണ്. ESP32 ശബ്ദം റെക്കോർഡ് ചെയ്യുകയും മറുപടി പ്ലേ ചെയ്യുകയും ചെയ്യുന്നു; സർവർ ഓൺലൈൻ സേവനങ്ങൾ ഉപയോഗിച്ചാണ് മറുപടി തയ്യാറാക്കുന്നത്. ഇതിൽ ഞാൻ ചെയ്ത പ്രവർത്തനങ്ങളും ഉപയോഗിച്ച ഉപകരണങ്ങളും വിശദീകരിക്കാം.

These are presentation drafts, not claims about who wrote particular code. Do not replace the bracketed contribution with work the pupil cannot substantiate.

## Build a record of the pupils' contribution

Keep a dated project folder with original sketches, component choices, wiring photographs, development notes, source history and test observations. Record outside assistance, tutorials, copied/adapted code, open-source libraries and AI coding help accurately. Acknowledging these inputs allows the pupil to explain the actual engineering work clearly.

For the required short construction video, show genuine stages: identifying components, wiring or assembly, making or adapting software, testing, finding a fault and demonstrating the finished result. Include the registered pupils' real involvement. Avoid a video consisting only of the completed model or a staged reconstruction of work they did not perform.

Useful attachments are an actual bill of materials, a block diagram, a wiring diagram for the exact board, a short code guide, a test table and an acknowledgements page. Keep API keys, passwords, device tokens and private account screens out of charts, printed code and videos. These attachments and privacy practices are project-preparation recommendations; the formal manual requirements are listed above.

## Demonstration and fallback plan

Recommended sequence:

1. Explain the problem and identify the physical components.
2. Ask one clear Malayalam question through the physical microphone and let Karen answer through its speaker.
3. Ask a relevant follow-up and explain how recent conversation helps supply context.
4. Point to the block diagram and identify where each service operates.
5. Explain one measured limitation and one improvement supported by actual test results.

Test the exact assembled model, power source and intended network before the event. Record complete physical turns, recognition mistakes, response delay, playback clarity and recovery after a network interruption. A successful browser text response or MP3 decoder log does not prove that the physical microphone and speaker work. The existing [exhibition runbook](../../EXHIBITION.md) supplies a fuller project acceptance sequence.

Bring the source, diagrams, construction video and a clearly labelled recording of a successful physical demonstration for discussion if the network fails. Browser text chat can help isolate an audio fault, but explain that it bypasses the hardware path. The repository's `DEMO_MODE` produces labelled scripted text and disables voice; it is not offline live AI. A recording or script is supporting evidence, not a substitute claim that the live Working Model operated during evaluation. [Demo and voice behaviour](../../../app.py)
